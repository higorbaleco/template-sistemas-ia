## Project Overview

**WhatsApp Disparador Multi-Tenant** — a message queue dispatcher backed by Evolution API, supporting multiple customer organizations and instances. Each org can connect multiple WhatsApp numbers, schedule bulk sends, and receive webhooks.

**Stack:** Node.js 20 LTS + TypeScript 5, Express, Prisma ORM, Bull (Redis queue), PostgreSQL 15, React 18, Docker.

**Critical Design:** Multi-tenant isolation via `organization_id` filter on ALL queries (non-negotiable).

### Key Boundaries

1. **API Routes** (`src/api/routes/`) — Express handlers, input validation, multi-tenant filtering
2. **Services** (`src/services/`) — Business logic (queue, Evolution integration), no HTTP
3. **Middleware** (`src/middleware/`) — Auth, error handling, request context
4. **Workers** (`src/workers/`) — Long-running processes (queue processor loop)
5. **Database** (`prisma/schema.prisma`) — Source of truth for schema and types

### Multi-Tenant Isolation Pattern

**Every database query MUST filter by `organization_id`.** This is not optional.

```typescript
// GOOD
const messages = await prisma.messageQueue.findMany({
  where: { organizationId, status: 'pending' },
});

// BAD — DATA LEAK
const messages = await prisma.messageQueue.findMany({
  where: { status: 'pending' },
});
```

Test any new endpoint with a second API key to verify isolation.

## Evolution API Integration

The `EvolutionClient` (`src/services/evolution.ts`) wraps Evolution's REST API:

- `connectInstance(instanceName)` → returns QR code (base64)
- `sendMessage(instanceName, { number, text })` → sends via WhatsApp
- `getInstanceStatus(instanceName)` → fetch connection status
- `logoutInstance(instanceName)` → disconnect

**Evolution expects:**
- Base URL: `EVOLUTION_API_URL` env var (e.g., `https://wpp-avraham.instantcode.com.br`)
- API key: `EVOLUTION_API_KEY` header (`apikey: <key>`)
- Instance names are unique identifiers created in the Evolution Manager

---

## Queue & Retry Logic

**MessageQueueService** (`src/services/queue.ts`):

1. Enqueue incoming message → DB record with status `pending`
2. Worker loop runs every 5 seconds, processes messages with `scheduledAt <= now()`
3. Calls Evolution API; if success, mark `sent`; if transient error (5xx, timeout), exponential backoff (5m → 10m → 20m... up to 24h, max 5 retries)
4. Permanent errors (invalid phone) → mark `failed`, no retry
5. All events logged to `message_logs` table

**Do not edit retry logic without consulting the spec (§7.1).**

## Testing Approach

**TDD:** Write test first, see it fail, implement, see it pass, commit.

- **Unit tests** (`tests/services/`) — mock external APIs (Evolution, Redis)
- **Integration tests** (`tests/api/`) — test routes + DB (use test fixtures)
- **Multi-tenant tests** — every route test must verify isolation (query with org2's key, should 404/403)

**Coverage targets:** 85%+ on routes, 90%+ on services.

```bash
npm test -- --coverage --collectCoverageFrom="src/services/**"
```

## Deployment & Running

### Local Development (Docker Compose)

```bash
docker compose up -d
npm run db:migrate
npm run dev                   # In one terminal
npm run queue:worker          # In another terminal
```

Access API at `http://localhost:3000`.

### Production (VPS / Docker)

1. Build image: `docker build -t disparador .`
2. Run with env vars from `.env.production`
3. Ensure PostgreSQL, Redis, and Evolution API are accessible
4. Run migrations: `npm run db:migrate`
5. Use process manager (pm2, systemd) to keep api + queue:worker running
6. Set up reverse proxy (nginx) with SSL
7. Configure Evolution webhooks to point to `{disparador_url}/webhooks/evolution`

## Troubleshooting

| Problem | Solution |
|---------|----------|
| "QR code not generating" | Check `CONFIG_SESSION_PHONE_VERSION` in Evolution `.env`; try updating in guide §20 |
| "Multi-tenant data leak" | Grep for queries without `organizationId` filter; add to all database calls |
| "Messages stuck in pending" | Check queue worker is running; verify Evolution API is reachable; inspect logs in `message_logs` table |
| "Webhook validation fails" | Ensure `WEBHOOK_SECRET` matches what Evolution is configured with |
| "Port 3000 already in use" | Kill process: `lsof -i :3000 \| grep LISTEN \| awk '{print $2}' \| xargs kill -9` |

## Key Decision Points

1. **Single vs. Multi-worker:** Currently one queue worker. To scale: run multiple workers (Bull handles distributed locking via Redis).
2. **Frontend:** Scaffolded React components in `src/frontend/` — not yet integrated into build. Future work: webpack/Vite bundler.
3. **Auth:** Bearer API key only. Future: add org user roles, JWT tokens for frontend.
4. **Storage:** PostgreSQL + Redis. No S3/blob storage yet (messages and logs stay in DB).
